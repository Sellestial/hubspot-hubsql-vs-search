# Fairness review before runs

Codex (gpt-6-sol) reviews the fairness of the v2 prompts, playbooks and runner before the scored runs.

## Findings

1. **The reviewed files are not demonstrably the files the runner will use.** `run.py:12–17,48,106` imports `bench.arms` and reads prompts, questions, the proxy, and the Python helper from paths outside this folder. It does not enforce the tool lists in the supplied `arms.py`; that depends on the unseen proxy. **Fix:** before the scored runs, have the runner record hashes of every loaded prompt and question file, the proxy and helper, and each arm’s actual MCP `tools/list` names, descriptions, and schemas. Assert that the tool list matches the arm definition. The supplied tool-description file covers only five tools and contains no schemas, so it cannot establish this now.

2. **The expert playbooks are not yet comparable guides to an exact answer.** For the free-text questions, `playbook-search.md:7–8` calls case-insensitive `EQ` counts exact, but the scoring rule also *trims spaces*; the supplied search description does not establish that `EQ` trims. `playbook-hubsql.md:6–7` suggests checking only a value or two, although every top-ten count and the ranking boundary must be correct. Small-`LIMIT` undercounts could change membership as well as counts. **Fix:** validate filter semantics, then give both expert arms explicit, equally rigorous instructions for normalization, every reported count, and the last-place boundary. Require them to mark an unproved ranking as such.

3. **The two free-text definitions may require work neither no-code playbook explains how to complete.** Both `questions.json:48,55` require grouping after trim and case folding. The supplied HubSQL description says string functions are unsupported; raw `GROUP BY` cannot implement that rule. Search has a 10,000-result ceiling acknowledged in its playbook, while its candidate-sampling advice does not guarantee coverage. **Fix:** establish a feasible exact method for each arm within the 15-minute limit, or state up front that these questions test whether the agent recognizes and reports an exactness limit. Do not score a confidently incomplete ranking as exact.

4. **Code arms have a potential route to information from other runs.** `run.py:45–60` creates sibling work directories and settings files, while the Bash sandbox denies only selected paths. It does not explicitly isolate previous work directories or benchmark outputs. Only code arms get Bash. **Fix:** give each run an isolated read scope containing its helper and necessary runtime files, remove accessible prior work directories, and deny reads of questions, reference answers, transcripts, and run artifacts. Check this with a sandbox probe before scoring.

5. **Giving every agent the exact definition is defensible, but it changes what the benchmark measures.** `run.py:33–34` gives all arms the same definition, so this is not an answer leak or a clear one-sided advantage. It supplies internal field names, option counts, and normalization rules that a real user may not know. Option counts especially help search plan exhaustive counts; normalization rules warn HubSQL away from raw grouping. **Fix:** describe the primary result as performance *with supplied business definitions*. If making claims about ordinary user requests, run a separately labeled, natural-language-only condition. Keep the exact definition for the scored condition because it removes genuine ambiguity.

6. **Q is a superset of S, so success in Q does not by itself show that HubSQL produced the answer.** `arms.py:8–17` gives Q every search tool plus `query_crm_data`. That is a valid test of the *availability* of HubSQL, but Q can answer through search. **Fix:** report the actual tool path for every Q result and attribute speed or accuracy to HubSQL only when its query was material to the answer. Keep conclusions about tool availability separate from claims about SQL itself.

7. **The scoring and reference rules need tightening before they can support exact claims.** `questions.json:62,69` asks for one decimal place but also uses a ±0.5% tolerance; a correctly rounded small value can fall outside that tolerance. The design promises an independent export before and after runs, but the supplied files do not show how “active,” empty values, UTC dates, or changing records are reconciled. **Fix:** specify the rounding convention and compare at the requested precision; freeze or reconcile data changes per question, and validate the export’s field semantics against the live tools. Predefine treatment of infrastructure errors separately from wrong answers and timeouts.

8. **The pre-run provenance and execution plan are incomplete.** `selection.md` says the 50-question pool was generated from field names, but the pool and evidence of its timing are outside the permitted files; this review cannot confirm that selected questions are held out from the five v1 pilot questions. The playbooks plainly incorporate v1 lessons—stratified sampling and low HubSQL grouped counts—but contain no visible answer values or candidate lists. `experiment-v2.md:45–47` also specifies a Sonnet subset and $100 stop that `run.py` does not enforce; the Sonnet subset includes S-expert but omits Q-expert. **Fix:** record the pool, selection seed, pilot overlap, and frozen playbook hashes; replace any reused pilot question if claiming a held-out test. Enforce the planned schedule and budget in the runner, or narrow the reported cross-model comparisons.

**Ready to run?** Not for a scored, publishable comparison. First establish the actual loaded files and tool lists, correct the expert methods and exact scoring rules, isolate code runs, and lock the question provenance and run protocol. The shared `system.md`, equal 900-second timeout, and within-question randomized arm order are sound as written.
