# Design review of the first test

Codex (gpt-6-sol) red-teams the first test (v1). This review is why the experiment was rebuilt.

## Task 1 — Methodological findings

The current runs are useful pilot data. They do not yet establish how a capable search agent compares with HubSQL. I reviewed [harness.py], [facts.md], and [article.html].

1. **The tested tools are not the remote MCP tools. Severity: decisive; this could change both accuracy and speed.** The harness supplies hand-written descriptions and schemas, calls REST endpoints directly, rewrites responses, and truncates them at 40,000 characters. `search_properties` is a custom keyword search that keeps only 30 matching properties. It also uses a private token, whereas the remote MCP connection uses an authorized user's access and its available tools vary by account. A reader cannot assume the agent would make the same calls through MCP. **Change:** connect the harness to the real remote server, save its `tools/list` schemas and `get_user_details` output, and allowlist the relevant tools. If that is impossible, capture the exact live schemas and compare representative calls and responses against MCP before calling the test a proxy. HubSpot documents both account-dependent tool availability and user-level permissions. [HubSpot MCP documentation](https://developers.hubspot.com/docs/apps/developer-platform/build-apps/integrate-with-the-remote-hubspot-mcp-server).

2. **Search was denied its strongest practical method. Severity: decisive; it could reverse the “cannot answer” result.** Without code or programmatic tool calls, the agent must move and aggregate hundreds of pages through its conversation. An agent with code can partition searches below the 10,000-result ceiling, retrieve the records, and compute an exact mean or frequency table. The company average needs roughly 905 pages at 200 records each; that is substantial work, not an impossibility. **Change:** add a search-plus-code arm that can call the *same authorized search tool* programmatically and aggregate locally. Pair it with a HubSQL-plus-code arm. Keep the no-code comparison as a separate, clearly measured workflow.

3. **The uncoached search run is an unusually weak top-title strategy. Severity: decisive for Q1.** All three runs began with one alphabetically sorted page and guessed titles. The author's later sample showed a candidate-generation approach could have found all ten. That manual check was also performed after seeing the miss. **Change:** preregister an expert-search arm with a concrete procedure: sample across multiple record or date strata, count candidate titles with exact filters, expand the sample until a stated stopping rule, and distinguish a discovered top ten from a proven top ten. Also test full enumeration in the code arm. Do not use the observed “(CRO)” result to tune the procedure.

4. **The tool descriptions give HubSQL unusually specific help. Severity: high; it could change tool-use success and call counts.** The HubSQL description supplies table names, supported aggregates, and the nonstandard `DATE_TRUNC` argument order. The search description gives capabilities but no comparable guidance on sampling, partitioning, or counting. The shared system prompt merely asks for exact numbers. **Change:** use the real MCP descriptions unchanged for the plain arms. Put identical business definitions and verification expectations in both prompts. Test expert playbooks as separately named arms for *both* tools; freeze them before confirmatory runs.

5. **HubSQL is being used to establish truth despite a demonstrated accuracy defect. Severity: decisive for exact-number claims.** Its `LIMIT 10` title counts varied and were up to 18 low. Larger limits agreeing with search counts for the identified titles do not prove there is no omitted title, nor that other grouped answers are exact. **Change:** export the relevant CRM records independently, aggregate them offline, and score the agent's raw answer against that result. Check HubSQL against the export too. Score title membership, ordering, and counts separately; an answer with the correct ranking and wrong counts is not fully correct. HubSpot provides a CRM export API suitable for an independent extract. [HubSpot exports documentation](https://developers.hubspot.com/docs/api-reference/legacy/crm/exports/guide).

6. **The five questions are exploratory and too easy to select after seeing results. Severity: high; it could change the apparent win rate.** They contain one particularly difficult free-text ranking and one large mean, alongside three tasks search completed. There is no documented question pool, selection rule, or excluded question log. **Change:** treat these five as pilots. Have a RevOps reviewer write a pool of realistic questions before running either arm; publish the full pool and eligibility rules, then use a recorded random seed to select the confirmatory set. Retain every selected question, including SQL failures.

7. **The population and answer definitions are not fixed tightly enough. Severity: high for close counts.** Records can change during sequential runs, and search indexing can lag. “No domain,” an average over nonempty employee counts, free-text title equality, ties, and “created in 2026 by record source” each need precise semantics. In October, “each month of 2026” also includes an unfinished year unless a cutoff is specified. **Change:** set a timestamp and timezone, freeze imports and edits during the test if possible, export before and after, and rerun or exclude questions whose underlying records changed. Specify null versus empty, exact value versus normalized value, tie order, numeric denominator and rounding, and whether record source means the current property or the value at creation.

8. **The stated “25 steps” is not the actual limit. Severity: high; it could explain failures.** `MAX_TURNS` counts model API turns; a turn may contain many tool calls, as the 89-call run demonstrates. The harness does not record whether a run hit that cap or a model/context limit. Its character clipping can also turn a tool result into incomplete JSON. **Change:** log model turns, tool calls, stop reasons, context usage, truncations, and budget exits separately. Set a generous common wall-time limit, such as 15 minutes, and a declared model-turn limit. Return valid paged or compact results instead of cutting JSON mid-string. Count a budget exit as a measured outcome, never as an unexplained refusal.

9. **There are too few independent runs, and only one confirmatory model. Severity: high for claims about agents generally.** Three repeats exist only for the two search failures; most outcomes have one run. The two HubSQL title runs share the same issue. **Change:** run every question and arm three times with fresh conversations and randomized order. Repeat the plain and expert comparison with a second model. Report per-question results and variation, rather than a single pooled success percentage.

10. **Timing is partly manufactured by the harness. Severity: high for the speed headline, lower for accuracy.** Calls execute serially even when the model requests several tools. Every search call sleeps 0.3 seconds and every HubSQL call 1.1 seconds after the response. These are neither maximum legal throughput nor necessarily how MCP schedules requests. Search's documented limit is five requests per second and 200 records per page. **Change:** use one shared, account-wide rate limiter at the applicable limits, permit independent concurrent calls where the real client does, honor `429` and `Retry-After`, and randomize arm order. Report model time, HubSpot/API time, throttle wait, retries, and total wall time separately. [HubSpot limit update](https://developers.hubspot.com/changelog/increasing-our-api-limits).

11. **The cost and “per 100 questions” numbers answer a different question from the experiment. Severity: high for the economic conclusion.** Hard-coded prices and the five-question mix yield an extrapolation, not observed usage. Different organizations will ask these categories at different rates. API cache usage, retries, code-runtime cost, and failed runs also need consistent treatment. **Change:** save provider usage and the price sheet date, calculate the actual cost of every attempt, and report the five question categories separately. Publish a per-100 figure only for an explicitly stated workload mix, with a sensitivity table for other mixes.

12. **The manual sampling result is neither random nor an independent validation. Severity: medium to high for the proposed Q1 workaround.** Ten evenly spaced locations in record-ID order can follow import batches or time periods, and “top 50 would have worked” was learned after the true top ten were known. **Change:** specify sampling strata and seeds before inspecting results; repeat across seeds; measure candidate recall and the subsequent exact-count cost. Use the independent full export to determine how often the sampling procedure misses a true top-ten title.

13. **The available record is not sufficient to audit failures. Severity: medium, but important for credibility.** The stored `tool_calls` contain inputs and result character counts, not full responses, status codes, latency, retry events, or the model's intermediate decisions. Exceptions become short error strings. **Change:** save redacted full transcripts and raw tool responses, HTTP status and rate-limit headers, model/version/settings, prompts, stop reasons, and a run manifest. Publish enough aggregate logs and code to reproduce scoring without exposing contact data.

14. **One prospect-heavy portal cannot establish a general HubSpot boundary. Severity: high for a general claim; lower for a portal-specific one.** Sparse deals, field cardinalities, import patterns, and permissions shape which tool wins. Restricting the agent to two tools also differs from allowing every relevant native read tool. **Change:** run the same registered set on a second, independently populated beta-enabled portal before making a general CRM claim. If the article is about a fully connected assistant, add an unrestricted read-only MCP arm; otherwise keep the experimental conclusion explicitly about the selected tool sets.

## Task 2 — A one-day redesign

**Question set.** Keep the existing five as published pilot results, outside the scored set. Ask an independent RevOps reviewer for at least 30 ordinary contact/company questions. Before querying answers, classify them into five groups: simple counts, bounded dropdown rankings, time-by-category breakdowns, free-text rankings, and numeric averages or sums. Publish the pool and exclusions; select two from each group with a recorded seed. Include only questions whose field, object, and requested population are available to both tools. Define the expected output format, cutoff, null handling, ties, and rounding in advance.

**Arms.**

| Arm | Agent access | What it tests |
|---|---|---|
| S | Real MCP search and property lookup, plain prompt | Typical no-code search use |
| S-expert | Same tools, frozen expert search playbook | Whether poor strategy caused the miss |
| S-code | Same search access callable from a code sandbox | Whether search can compute the answer programmatically |
| Q | Real MCP HubSQL and the same property lookup, plain prompt | Typical no-code HubSQL use |
| Q-expert | Same tools, frozen SQL verification playbook | Whether dialect and beta accuracy issues can be managed |
| Q-code | HubSQL callable from the same sandbox | Matched comparison when code is available |

Use the real MCP server for S and Q, saving `tools/list` and the account-access check. If programmatic MCP invocation cannot be made available to code, use the corresponding REST endpoints with the **same OAuth principal**, then verify a set of equivalent queries returns the same record population. A private token with broader access would confound that arm. HubSpot says the remote server's available tools and objects depend on the account and user. [HubSpot MCP documentation](https://developers.hubspot.com/docs/apps/developer-platform/build-apps/integrate-with-the-remote-hubspot-mcp-server).

**Runs and prompts.** Use Opus 5.5 for three fresh repeats of all ten questions in all six arms: 180 runs. Run two repeats of S, S-expert, and Q on a second model, such as Sonnet 5.5: 60 more. Pin exact model versions and settings. Give all arms the same short system instruction, business definitions, user question, and 15-minute ceiling. The expert playbooks may describe methods but must contain no answer, title candidate, or lesson learned from these ten questions. Randomize arm order within each question and run in small paired blocks, so portal changes and API load do not favor one arm.

**Truth and scoring.** Independently export the required contacts and companies once before testing and again afterward. Aggregate by record ID offline; inspect any differences. Score:

- exact complete answer, including every requested count;
- ranking membership and order, separately from numeric counts;
- abstention, unsupported certainty, and errors;
- total tool calls, records transferred, retries and rate limits;
- wall time split into model, HubSpot, and enforced wait;
- actual model tokens and cost per attempt.

For a mean, declare the non-null denominator and a rounding tolerance before running. For rankings, declare raw-value normalization and tie handling. Do not “correct” a HubSQL answer after the fact because a larger `LIMIT` would have fixed it.

**Capacity and budget.** At 200 records per page, a complete scan of the 490,657 titled contacts is about 2,454 pages; the company-size scan is about 905. At the stated five-search-request-per-second ceiling, their theoretical minimum API pacing is roughly 8.2 and 3.0 minutes respectively, before server latency and partitioning. A few repeated code scans therefore fit in a day. Use an account-wide search limiter of at most five requests per second and HubSQL limiter of at most one per second, track the stated 10,000 HubSQL requests/day, and handle retries explicitly. The pilot's search runs around $0.60–$0.98 suggest the no-code Opus portion is likely the main API expense. Meter spend live, reserve $20 of the $100 for retries, and stop only at complete, randomized question blocks if the budget is reached; report any unrun blocks. [Search API limit update](https://developers.hubspot.com/changelog/increasing-our-api-limits).

**Decision rule.** Predeclare both correctness and usefulness. On this registered set, call search *sufficient for the workflow* only if its best applicable arm matches the paired HubSQL arm on exact answers across the hard questions **and** meets the chosen operational target, for example a five-minute answer and no more than $0.50 in model cost per question. If S-code is exact while S and S-expert fail, the result is specifically a **no-code MCP workflow advantage** for HubSQL, not an inability of search to calculate the answer. If both code arms are exact but HubSQL is consistently much faster or cheaper, its advantage is efficiency. If Q returns wrong counts, speed does not make it the accuracy winner. Report outcomes by question category; ten questions do not justify a universal win-rate claim.

## Task 3 — Text that still needs attention

- The headings “Search can only count what it thinks to ask for” and “Averages are out of reach for search” become false if the code arm succeeds. State the measured workflow and result instead.
- The recommendation to ask HubSQL for `LIMIT 60` is based on a handful of observations about one query. Present it as an observed beta behavior only after independent verification; do not imply it guarantees exact counts.
- Remove the $77 versus $2.55 “per 100 questions” headline unless the redesigned study supplies a declared question mix and observed costs. The current five runs do not establish that workload.
- “The correct answers came from HubSQL” conflicts with the documented varying counts. The new article should name the independent export as ground truth and score HubSQL's low counts as errors.
- The broad conclusion about what an AI connected to a CRM can trust must follow the tested arms. The current draft moves between restricted tool access, MCP generally, and code-capable agents as though they were one setup.
